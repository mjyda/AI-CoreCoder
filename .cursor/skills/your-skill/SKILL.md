# 构建小型项目

## 目标

交付一个可运行的小型项目，具备清晰结构、可用核心功能和基础验证。

## 关键执行规则

- 只有在工具执行成功后，才能声明文件已创建或已更新。
- 对于任何构建任务，必须先完成真实文件操作，再汇报结果。
- 严禁伪造运行输出；若命令未执行，必须明确说明“未执行”。
- 工具调用失败时，先汇报错误，再用修正后的命令重试。
- 在最终答复前，必须确认目标文件存在且包含预期代码。

## 工作流

按以下顺序执行：

1. 澄清范围：
   - 确认项目类型、运行环境和核心功能。
   - 若需求有歧义，编码前先提出简洁问题。
2. 制定实现计划：
   - 给出最小可行目录结构。
   - 先定义核心功能里程碑，再考虑可选增强。
3. 搭建脚手架：
   - 创建目录和初始文件。
   - 补齐本地运行所需的依赖与配置文件。
4. 实现功能：
   - 优先完成主流程（happy path）。
   - 为用户输入和外部失败添加基础错误处理。
   - 保持代码简单清晰，避免过度设计。
5. 验证：
   - 运行相关测试或可执行检查命令。
   - 在最终交付前修复明显失败项。
6. 交付：
   - 总结已完成内容。
   - 给出运行方式和下一步改进建议。

## 必做验证清单

在声明“已完成”前，必须逐项确认：

- [ ] 目标目录存在（例如 `demo/`）
- [ ] 必需文件已创建（例如 `demo/main.py`）
- [ ] 每个必需文件中包含核心代码
- [ ] 至少有一条运行/测试命令执行成功
- [ ] 最终答复包含实际执行命令与真实结果摘要

## 构建约束

- 默认选择稳定方案，不提供过多可选项。
- v1 仅实现用户明确要求的功能范围。
- 采用增量式修改，并在重要改动后立即验证。
- 文件名、函数名、命令名保持一致性。

## 协作编排

当以下技能可用时，按固定流水线协作执行：

- `api-dev-zh`：接口与核心业务实现
- `test-coverage-zh`：补齐测试与验证
- `bug-fix-zh`：缺陷定位与最小修复
- `code-review-zh`：质量审查与风险识别
- `refactor-zh`：在行为不变前提下优化结构

阶段顺序与门槛如下：

1. 需求与计划阶段（当前技能主导）
   - 输出最小可行范围、目录结构、实现步骤。
   - 门槛：需求边界清晰，文件结构确定。
2. 实现阶段（优先应用 `api-dev-zh`）
   - 先实现核心功能与主流程，再补基础错误处理。
   - 门槛：核心功能可运行，关键文件已落地。
3. 测试阶段（应用 `test-coverage-zh`）
   - 为关键路径、异常路径、边界条件补测试。
   - 门槛：至少一条测试或运行命令通过。
4. 缺陷修复阶段（必要时应用 `bug-fix-zh`）
   - 对失败项做根因分析并最小修复，再次验证。
   - 门槛：无阻塞性错误，主要用例通过。
5. 审查与收敛阶段（应用 `code-review-zh`，必要时 `refactor-zh`）
   - 先审查正确性/风险，再做小步重构优化。
   - 门槛：高风险问题清零，结构可维护。
6. 交付阶段（当前技能主导）
   - 输出交付说明、执行记录、已知限制、下一步建议。

编排执行规则：

- 不得跳过“测试阶段”和“交付阶段”。
- 若任一阶段失败，回退到对应阶段修复，不直接宣告完成。
- 每阶段结束都要给出可验证证据（文件变化或命令结果）。
- 阶段结论必须与真实执行一致，禁止推测性完成描述。

## 反幻觉与反重复约束

为防止“看起来完成但实际未完成”的输出，必须遵守：

1. 证据绑定
   - 每个“已完成”结论必须绑定至少一条真实证据：
     - 文件证据：实际创建/修改的文件路径；
     - 命令证据：实际执行命令及结果摘要（成功/失败）。
   - 无证据的结论一律改写为“计划/建议”，不得写成“已完成”。
2. 禁止猜测与伪造
   - 禁止使用“应当通过”“大概率成功”“可以认为完成”等推测性表述替代验证。
   - 禁止生成未执行命令的输出结果。
   - 当用户明确要求“不要运行命令”时，必须切换为静态报告模式：
     - 明确声明“未执行命令，以下为静态结果”；
     - 不得出现“测试已通过/运行成功”等已验证语气。
   - 静态模式允许读取真实文件（只读工具）；禁止用“没有访问能力”作为默认理由。
   - 若未读取到任何真实文件内容，必须明确“证据不足，无法完成静态审查”并停止结论，不得输出假设性分析。
3. 文本去重
   - 最终交付中同一功能点只允许出现一次，不得重复堆叠。
   - “已完成功能”“项目结构摘要”“已知限制”三部分不得交叉重复。
   - 输出前进行自检：若存在重复段落、重复列表项或结构污染，先重写再输出。
4. 失败透明化
   - 任何失败必须显式记录：失败步骤、错误摘要、下一步处理。
   - 不得在存在未解决失败时使用“全部完成”或“全部通过”。
5. 危险操作保护
   - 对删除、覆盖、批量修改命令必须先说明风险并请求确认。
   - 未获确认不得执行破坏性操作（如批量删除文件）。

## 最终输出闸门

在交付最终答复前，必须执行一次“输出净化与一致性检查”：

1. 噪声清理
   - 删除所有工具调用标签与过程文本，如 `<tool_call>`、`<function=...>`、`<parameter=...>`。
   - 最终答复中不得回显原始工具协议片段。
2. 一致性修正
   - 若输出中出现前后矛盾（例如先说目录为空，后又读取到文件），以最新可验证证据为准重写结论。
   - 禁止保留已被后续证据推翻的描述。
3. 命令三元组
   - “实际执行命令”部分必须使用三元组记录：
     - 命令
     - 状态（成功/失败）
     - 关键结果摘要（1行）
   - 仅列出真实执行过的命令，不得列计划命令。
4. 固定结构
   - 最终答复仅允许以下 7 个固定标题，不得插入额外章节：
     1. 已实现功能
     2. 项目结构摘要
     3. 实际执行命令
     4. 验证结果
     5. 已知限制
     6. 下一步建议
     7. 协作编排执行记录
5. 自检重写
   - 若任一规则不满足，必须先自动重写一次再输出。
   - 重写后仍不满足时，明确声明“输出校验未通过”并说明缺失项，不得假装完成。

## 输出格式

汇报完成时必须包含：

1. 已实现功能
2. 项目结构摘要
3. 实际执行过的运行/测试命令
4. 已知限制
5. 下一步建议迭代
6. 协作编排执行记录（按阶段列出）
