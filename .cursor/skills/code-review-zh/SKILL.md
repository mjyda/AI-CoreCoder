# 代码审查（中文）

## 目标
输出可执行的审查意见，优先发现会导致故障、数据错误或安全风险的问题。

## 审查顺序
1. 正确性：逻辑是否正确，边界条件是否覆盖。
2. 回归风险：改动是否破坏原有行为，兼容性是否受影响。
3. 安全性：输入校验、命令执行、路径处理、权限控制。
4. 可维护性：命名、结构、重复逻辑、错误处理质量。
5. 测试：是否有足够测试覆盖关键路径和失败路径。

## 输出格式
按严重级别输出：
- 严重：必须修复，阻塞合并。
- 重要：建议本次修复。
- 建议：可后续优化。

每条意见需包含：
- 问题描述
- 风险说明
- 建议修复方向

## 执行规则
- 没有证据时不下结论。
- 先给问题，再给简短总结。
- 不把代码风格问题放在高优先级之前。

## 反幻觉与反重复规则
1. 证据绑定
   - 每条“严重/重要”问题必须绑定可核验依据（代码片段、文件路径或命令结果）。
   - 无证据的问题降级为“疑似风险”并明确待验证。
2. 禁止伪造
   - 不得虚构已执行测试或已复现结果。
   - 用户要求“不要运行命令”时，必须声明“未执行命令，以下为静态审查结论”。
   - 静态审查允许读取真实文件（只读）；不得默认声称“无法访问文件系统”。
   - 若未读取到真实代码内容，必须明确“证据不足，无法给出审查结论”，不得输出假设性问题清单。
3. 文本去重
   - 同一问题只报告一次，不得在不同小节重复堆叠。
   - 输出前删除重复结论与重复建议。
4. 失败透明
   - 存在阻塞问题时，不得给出“可直接合并”的结论。
5. 危险操作保护
   - 审查过程中若需要删除/覆盖文件验证，先说明风险并请求确认后再执行。
