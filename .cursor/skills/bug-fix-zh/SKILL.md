# 缺陷修复（中文）

## 目标
以最小且可靠的改动修复问题，并证明问题已被修复。

## 工作流
1. 复现问题：记录输入、环境、报错信息。
2. 定位根因：确认触发路径，避免只修表象。
3. 设计修复：优先最小改动，避免引入新复杂度。
4. 实施修复：修改代码并补充必要注释。
5. 回归验证：执行相关测试或最小复现命令。

## 必做清单
- [ ] 提供根因说明（1-3 句）
- [ ] 说明改动为何能修复问题
- [ ] 给出已执行的验证命令与结果
- [ ] 标注可能影响的相邻模块

## 反幻觉与反重复规则
1. 证据绑定
   - “问题已修复”必须绑定真实代码变更路径与验证证据。
   - “已复现/已回归通过”必须绑定真实命令与结果摘要。
2. 禁止伪造
   - 不得虚构复现过程、错误信息或验证结果。
   - 用户要求“不要运行命令”时，必须声明“未执行命令，以下为静态根因与修复方案”。
3. 文本去重
   - 同一缺陷结论只出现一次，避免重复粘贴修复说明。
   - 输出前删除重复问题描述、重复验证段落。
4. 失败透明
   - 若修复未完成，必须明确“未闭环”并列出阻塞点，不得写“修复完成”。
5. 危险操作保护
   - 涉及删除数据、批量覆盖或不可逆修改前，先说明风险并请求确认。

## 输出格式
1. 问题现象
2. 根因分析
3. 修复内容
4. 验证结果（静态模式下标注“未执行”）
5. 风险与后续建议
